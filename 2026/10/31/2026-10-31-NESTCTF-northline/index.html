2026-10-31-NESTCTF-northline

2026-10-31 11 min read 5.1k 字
#网络安全 #CTF #Web #MCP

资料说明：原记录中提及的本机脚本及题目附件未随本文附上，相关文件名仅用于说明当时的复现流程。

Crossed Signals（Northline Service Desk）· 四层门，全靠“同一个值传两遍、两侧不同源”

平台题目名：Crossed Signals（Web，655 分，10:19:33 提交）。内部代号 northline，目标 zu9tte01。

目标：http://zu9tte01.nestctf.cyberpeace.cn:58080/（内网 172.78.112.236）
凭据：advisor@northline.test / Service-Desk-2026（题面给的服务台账号）
复现：py -3.13 solve_final.py

一句话

整题的骨架是 “同一个语义值在请求里出现两次，而校验与执行各自只看其中一次”：VIN 走 HTTP 头与 JSON body 各一份、工具名走 Mcp-Name 头与 params.name 各一份、bundle 的 release 状态走 notes 接口的批量赋值。三处错位叠起来，把受限车辆的 private/recovery.txt 从封存包里取了出来。

MCP POST /mcp，JSON-RPC 2.0，MCP-Protocol-Version: 2026-07-28，工具参数 schema 里带 x-mcp-header 映射

5. 脚本

solve_final.py 一条链跑完：登录 → 头/体错位取两个 ref → Mcp-Name 错位导出 → notes 批量赋值批准 → 下载解压 → 正则取 token。二次运行 token 稳定。

6. 顺手记下的接口细节

端点 行为
POST /api/login {username,password} → {token,expires_in,role}；token 是 32 字节 base64url，不是 JWT
GET /api/me 含 assigned_vins、tool_endpoint、protocol_version
GET /api/cases 跨车队元数据可见，access 区分 assigned / restricted
POST /api/bundles/<id>/notes note 必填（{} → invalid_note），其余任意字段被回写进记录
GET /api/bundles/<id>/download 需 release_state=approved
PATCH / PUT 501（服务端只实现 GET/POST）
resources/*、prompts/* unsupported_method（网关只做 tools）

7. 踩坑

坑 现象 解决
_meta 元数据 -32600 Invalid request metadata 三个 io.modelcontextprotocol/* 字段一个都不能少
Mcp-Method 与 body 不符 -32020 HeaderMismatch 头与 body 的 method 必须一致
只填头不填体 仍然 403 两处都要改：头放自己、体放目标
notes 只发 note 200 但仍 pending 必须显式塞 release_state:"approved"

8. 修复建议

  1. VIN 只保留一个真源：只信 Mcp-Param-VIN 或只信 body，二者不一致直接 400。
  2. 工具 scope 用 body 的 name 判，不要用可伪造的头。
  3. notes 接口做字段白名单，release_state 只能由服务端状态机推进（且需要 security 角色）。
  4. 预览包不要和完整包共享同一份 manifest，私有条目名本身就是信息泄露。

9. 一句话总结

MCP 这类“头 + JSON-RPC body”双通道的接口，天生适合出参数错位题：网关为了做鉴权/限流会把关键参数提到头里，而执行层又从 body 里取。只要两处不是同一个来源，就一定有一处是假的。
